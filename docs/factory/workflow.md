# 工程・役割・停止と振り返り

[設計書の入口](README.md) ｜ [合格判定と保護](verification.md) ｜ [実装状況と後続課題](implementation-status.md)

## 1. 工程と成果物

発注前に、人が AI と要求整理・要件定義・UIUX を検討し、作るもの・利用者の目的・合格条件を Issue に落とす。変更の規模や不確実さに応じて短く繰り返し、実装方法の設計は計画で扱う。具体的な調査手法や UIUX の合否基準は各製品で決める。

| 工程 | 担当 | 次工程へ渡すもの |
|---|---|---|
| 発注 | 発注者（人） | 作るもの・合格条件を記載した Issue。正本は本文と発注者が確認した更新とし、その他のコメントや PR 本文は未確認の入力として扱う |
| 計画 | 計画役 | `docs/exec-plans/` に置く変更範囲・手順・検証方法 |
| 合格シナリオ | シナリオ作成役 | 実行できる合格条件を `tests/scenarios/` にする。[別 Issue・PR で先に承認・マージする](verification.md#3-合格シナリオの守り方) |
| 実装 | 実装役 | 1 Issue = 1 worktree = 1 ブランチ = 1 PR の変更。独立した Issue は並行して進める |
| 機械検証 | 検証役・CI | [対象版と実行内容を確認できる証拠](verification.md#合格判定に必要な証拠) |
| レビュー | レビュー役 | Issue・計画・差分・検証証拠に基づく指摘と判定。実装中の会話は引き継がない |
| マージ | 人 | CI・レビュー・必要な承認を確認したうえでのマージ。当面は全危険度で人が実施する |
| 振り返り | 振り返り役・工場長・発注者（人） | 結果・介入理由・指標・改善候補。公開後の発見は次の発注へ、人の判断でハーネス改善へ戻す |

機械で判定できない合格条件は、人の確認項目として Issue に残し、実行シナリオの合格と分けて記録する。画面の見た目が案と一致したことだけで、利用者の目的を達成したとは判定しない。

## 2. 役割と権限

人の発注・承認と AI の進行管理、実装とシナリオ変更、作成と承認を分ける。

| 役割 | 担当・できること | できないこと |
|---|---|---|
| 発注者（人） | 大野。作るもの・合格条件・承認を決め、ハーネス改善を判断する | 自己申告だけを合格の証拠としない |
| 工場長 | 強いモデルの指揮役 AI。作業を分解し、依存関係と変更ファイルの重なりから並行可否を判断する。割り当て・進行・統合順を管理する | 仕様の勝手な確定、人の承認の代行、工場ルールの無承認変更 |
| 計画 | 強いモデル。Issue を基に変更範囲と検証方法を計画する | 未決の仕様・合格条件の勝手な確定 |
| シナリオ作成 | 合格条件を実行するシナリオを作る | 実装の都合での合格条件の緩和、自分が書いた PR の自己承認 |
| 実装 | Claude／Codex を交互に担当させ、計画に沿って実装・修正する | シナリオ本文・実行条件・比較処理・期待値の実装 PR での変更（必要なら別 Issue・PR）。自己承認・マージ |
| 検証 | CI で機械検証し、出力と証拠を確認する | 合格条件の変更による検証通過、未確認の成功扱い |
| レビュー | 実装しなかった方が別の文脈で要件・正しさを確認する | 自分が実装した PR の承認、人の必須承認・マージの代行 |
| 振り返り | 結果・指標・介入理由をまとめ、工場長と発注者へ改善候補を返す | 失敗の成功への書き換え、工場ルール変更の無承認確定 |

モデル名・版や役割ごとの最終選定は [未決](implementation-status.md#未決事項)。原則0の Gemini は可読性・可搬性の対象で、具体的な担当を決めたものではない。

## 5. 停止・再開と結果の記録

| 条件 | 動作 |
|---|---|
| レビューからの修正往復 | 2 回まで。さらに必要なら停止して人へ返す |
| CI の同じ失敗が連続 | 3 回続いたら停止して人へ返す |
| 却下 | 再試行しない |
| 仕様があいまい | 質問を返して停止し、推測で実装を続けない |

却下・質問待ち・承認待ちは工程の状態として、下の結果分類と分けて記録する。無応答や timeout は承認ではなく、承認が必要な工程は停止を維持する。

| 結果分類 | 定義 | 対処 |
|---|---|---|
| 成功 | 合格条件を証拠で確認できた | 次工程へ進む。人の承認を代替しない |
| 欠陥 | 成果物が合格条件を満たしていない | 成果物を修正し、指示・文脈・評価の不足も調べてハーネス改善候補を残す |
| 障害 | 環境・権限・道具の不足で進めない | 環境を整える。成果物や合格条件を緩めて回避しない |
| 手作業 | 意図して人の担当とした、または人に引き取った | 引き取った範囲と理由を残し、自動化との境界を振り返る |

修正後は機械検証とレビューへ戻る。環境復旧後も対象版で検証し直す。停止回数は引き継ぎ、自動的に数え直して上限を回避しない。却下・停止後の新たな発注判断は人へ戻す。

暫定の記録先は対象 Issue または PR。工程状態・結果分類・証拠・回数・介入理由・改善候補を残し、未確認を成功としない。上限到達後に人が続行を指示した場合は、その指示・再開工程・以後の回数の扱いも記録する。

## 6. 指標

各 Issue／PR の検証・レビュー・振り返りの証拠から記録する。

| 指標 | 記録する内容 |
|---|---|
| 初回 CI 通過 | 最初の CI 実行が通ったか |
| 手直しなしのマージ | 修正せずにマージできたか |
| 修正往復回数 | レビューに対する修正の往復数 |
| 結果の分類 | 成功／欠陥／障害／手作業 |
| 人が介入した理由 | あいまいな仕様、停止条件、承認などの実際の理由 |
| 所要時間 | 作業にかかった時間 |
| 公開後の差し戻し件数 | 公開後に差し戻しとなった件数 |

工場長が指標を整理し、発注者がハーネス改善と軽・中の自動マージ移行の判断材料にする。記録形式・集計条件などは [未決事項](implementation-status.md#未決事項) を参照する。
