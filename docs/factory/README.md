## 0. 原則0：ツール非依存

工場の知識とルールは普通の Markdown とスクリプトだけで書く。Claude Code・Codex・Gemini のどれでも同じ内容を読んで動けるようにし、特定ツール専用の保存先・hook・コマンドに依存させない。

入口はリポジトリルートの AGENTS.md、詳細は `docs/` とする。強制手段は CI・ブランチ保護・CODEOWNERS。ツール内の設定やエージェントの自己申告を、これらの代わりにしない。強制の仕組みが未実装の間は、人のレビューで確認し、実装済みと誤認させない。

## 1. 工程と成果物

発注前に、人が AI と要求整理・要件定義・UIUX の検討を行い、作るもの・利用者の目的・合格条件を Issue に落とす。これらは不要になるのではなく、変更の規模や不確実さに応じて短く繰り返す。実装方法の設計は計画で扱い、公開後の発見は次の発注へ戻す。具体的な調査手法や UIUX の合否基準は各製品で決め、この文書では追加しない。

| 工程 | 担当 | 成果物・次工程へ渡すもの |
|---|---|---|
| 発注 | 発注者（人） | Issue に作るものと合格条件の文章を置く。正本は Issue 本文と、発注者が確認した更新とする。その他のコメントや PR 本文は未確認の入力として扱う |
| 計画 | 計画役 | `docs/exec-plans/` に変更範囲・手順・検証方法の計画を置く |
| 合格シナリオ | シナリオ作成役 | Issue の合格条件のうち実行できるものを `tests/scenarios/` にする。実装に先行する別 Issue・PR で人の承認を受ける |
| 実装 | 実装役 | 1 Issue = 1 worktree = 1 ブランチ = 1 PR で変更する。独立した Issue は並行して進める |
| 機械検証 | 検証役・CI | 対象変更の CI 結果と検証の証拠を残す。未確認は合格にしない |
| レビュー | 実装と別モデルのレビュー役 | 実装中の文脈を引き継がず、Issue の仕様・合格条件、計画、差分・検証証拠から指摘と判定を残す |
| マージ | 人 | CI・レビュー・必要な承認を確認してマージする。当面は全危険度で人が実施する |
| 振り返り | 振り返り役・工場長・発注者（人） | 結果の分類、介入理由、指標、改善候補を記録し、人の判断でハーネスの改善へ戻す |

機械で判定できない合格条件は、人の確認項目として Issue に残し、実行シナリオの合格と分けて記録する。画面の見た目が案と一致したことだけで、利用者の目的を達成したとは判定しない。

計画・シナリオの保存と運用を支える仕組みは後続で整備する。CI が通っただけで仕様を満たしたとは判定せず、合格シナリオとレビューの証拠も確認する。仕様があいまいな場合は、実装役の推測で埋めず [停止条件](#5-止めどころ) に従う。

### 検証で渡す証拠

検証役は Issue の合格条件・計画・対象差分を入力とし、実装役の自己申告だけでなく、CI の記録または再実行の出力で確認する。証拠には次を残す。

- 対象の head commit SHA。
- 実行したコマンド、exit code、出力・ログへの参照。
- 実行したシナリオ・テストの対象と件数。期待する対象との対応。
- 合格条件ごとの判定と、人の確認が必要な項目の確認記録。

exit 0 だけでは合格にしない。必要な検査が 0 件、対象外、未実行の場合は未確認として残す。head が変わったら変更後の版で証拠を取り直す。レビューの再実施範囲は工場長が差分と影響から判断し、理由を記録する。未確認の項目が残る間は合格扱いでマージへ進めない。

## 2. 役割と権限

役割は責務の分離を表す。特に、人の発注・承認と AI による進行管理、実装とシナリオの変更権限、作成と承認を分ける。

| 役割 | 担当・できること | できないこと |
|---|---|---|
| 発注者（人） | 大野。作るもの・合格条件・承認を決め、ハーネス改善を判断する | エージェントの自己申告だけを合格の証拠としない |
| 工場長 | 強いモデルの指揮役エージェント。作業を分解し、依存関係と変更ファイルの重なりから並行可否を判断する。工程の割り当て・進行・統合順を管理する | 仕様を勝手に確定しない。人の承認を代行しない。工場のルールを無承認で変えない |
| 計画 | 強いモデル。Issue を基に変更範囲と検証方法を計画する | 未決の仕様・合格条件を勝手に確定しない |
| シナリオ作成 | Issue の合格条件を実行するシナリオを作る。具体的なモデルは未決 | 実装の都合で合格条件を緩めない。自分が書いた PR を自分で承認しない |
| 実装 | Claude／Codex を交互に担当させ、計画に沿って実装・修正する | シナリオ本文・実行条件・比較処理・期待値を実装の都合で変更しない。自分の PR を承認しない。マージしない |
| 検証 | CI で機械検証し、検証役が出力・証拠を確認する。検証役のモデルは未決 | 検証を通すために合格条件を変更しない。未確認を成功と記録しない |
| レビュー | 実装しなかった方が担当。別の文脈から要件・正しさを確認する | 自分が実装した PR を承認しない。人の必須承認・マージを代行しない |
| 振り返り | 結果・指標・介入理由をまとめ、工場長と発注者（人）へ改善候補を返す。モデルは未決 | 失敗を成功に書き換えない。工場のルール変更を無承認で確定しない |

v0.1 のモデル方針は「工場長・計画は強いモデル、実装は Claude／Codex を交互、レビューは実装しなかった方」。モデル名・版や役割ごとの最終決定は未決とし、運用しながら決める。原則0は Gemini も含む可読性・可搬性の要件であり、現時点で Gemini の具体的な担当を決めるものではない。

## 3. 合格シナリオの守り方

合格条件の文章は Issue に書き、実装役にも見せる。実行するシナリオは `tests/scenarios/` に置く。実装役から隠すことではなく、変更権限の分離によって、シナリオ本文に加え、実行対象・実行条件、比較処理、期待値の生成元の無断変更を防ぐ。実行設定やヘルパーの変更でシナリオを除外したり期待値を緩めたりする経路も保護対象とする。変更権限の分離だけで、期待値の妥当性や不具合の検出力が保証されるわけではない。

- 実装の PR が `tests/scenarios/` に触れたら CI を失敗させ、ブランチ保護の必須チェックでマージを止める。
- シナリオを変更する PR には CODEOWNERS とブランチ保護を組み合わせ、人の承認を必須にする。CODEOWNERS ファイルを置くだけで強制できたとは扱わない。
- シナリオの修正が必要になったら、実装の PR で直さず、Issue の合格条件との整合を人に確認し、別の Issue・PR にシナリオ変更を分離する。実装 Issue には依存先を記録する。

シナリオの追加・変更は実装とは別の Issue・worktree・PR とし、人の承認を経て実装より先にマージする。これにより「1 Issue = 1 PR」を維持する。実装前のシナリオが main の必須 `ci` を壊さず、実装 PR では必要なシナリオが必ず実行される方式は未決で、後続で定める。この方式と保護の整備を、工場に製品を流す前提とする。

実装 PR とシナリオ変更 PR を CI がどう識別するか、判定に影響するファイルの対応表、CODEOWNERS の具体的な所有者・保護設定は未決。CI・ブランチ保護・CODEOWNERS による判定と承認必須化を実装する後続 Issue で定める。対応表が決まるまでも、判定に影響する変更は実装 PR の通常変更として扱わず、人へ確認し、必要な変更を別 Issue・PR に分離する。

エージェントが GitHub 上で動く主体と、人の承認主体をどう分けるかも未決。役割の分離を同一アカウント上の自己申告だけで強制済みとせず、エージェントが作成した PR を人が承認してマージできる構成を、承認必須化の前提として検証する。具体的なアカウント・権限構成はここでは決めない。

## 4. 危険度の区分

危険度は変更ファイルの場所で機械的に判定する設計とする。

| 区分 | 対象 | v0.1 の扱い |
|---|---|---|
| 軽 | `content/`・`docs/`（聖域を除く） | 人がマージする |
| 中 | `app/`・`components/`・テスト（`tests/scenarios/` を除く） | 人がマージする |
| 重 | 依存（`package.json`・`pnpm-lock.yaml` など） | 人がマージする |
| 聖域 | `infra/`・秘密情報・認証・AGENTS.md・CI・`tests/scenarios/`・`docs/factory/` | 人のレビュー・承認を必須とし、人がマージする |

`docs/factory/` は `docs/` の一部でも聖域とする。複数区分に該当する変更は重い側で扱う。秘密情報・認証などの具体的なパス対応表、対象外パスの扱いを含む判定仕様は未決。パス判定の成功を、秘密情報を保存してよいという許可にはしない。秘密情報の取り扱いは既存の AGENTS.md に従う。

当面はすべて人がマージする。実績を見て軽・中を自動マージへ移す方針だが、移行時期・合格基準は未決。重・聖域の自動マージは v0.1 では定めない。この設計書と AGENTS.md の変更も聖域であり、人（大野）の承認が必要。

## 5. 止めどころ

| 条件 | 動作 |
|---|---|
| レビューからの修正往復 | 2 回まで。さらに修正が必要なら停止して人へ返す |
| CI の同じ失敗が連続 | 3 回続いたら停止して人へ返す |
| 却下 | 再試行しない |
| 仕様があいまい | 質問を返して停止する。推測で実装を続けない |

結果は「成功／欠陥／障害／手作業」で記録し、次の対処につなぐ。

| 分類 | 定義 | 対処 |
|---|---|---|
| 成功 | 合格条件を証拠で確認できた | 証拠を残し、次工程へ進む。成功の記録は人の承認を代替しない |
| 欠陥 | 成果物が合格条件を満たしていない | 成果物を修正し、指示・文脈・評価の不足も調べてハーネス改善候補を残す |
| 障害 | 環境・権限・道具の不足で進めない | 環境を整える。成果物や合格条件を緩めて回避しない |
| 手作業 | 意図して人の担当とした、または人に引き取った | 引き取った範囲と理由を残し、自動化との境界を振り返る |

却下・質問待ち・承認待ちなどの工程状態は、結果の分類と分けて記録する。無応答や timeout は承認ではなく、承認が必要な工程は停止を維持する。修正後は機械検証とレビューへ戻る。環境復旧後も対象版で検証し直す。どちらも上の停止回数を引き継ぎ、自動的に数え直して回避しない。

暫定の記録先は対象 Issue または PR とし、状態・結果分類・確認した証拠・回数・人が介入する理由・改善候補を残す。未確認を成功としない。上限到達後に人が続行を指示した場合は、その指示、再開する工程、以後の回数の扱いも記録する。

「同じ失敗」の機械判定方法や結果分類の詳細な記録形式は未決。却下・停止後の新たな発注判断は人へ戻し、自動再試行で停止条件を回避しない。

## 6. 指標

各 Issue／PR の検証・レビュー・振り返りの証拠から、次を記録する。

| 指標 | 記録する内容 |
|---|---|
| 初回 CI 通過 | 最初の CI 実行が通ったか |
| 手直しなしのマージ | 修正せずにマージできたか |
| 修正往復回数 | レビューに対する修正の往復数 |
| 結果の分類 | 成功／欠陥／障害／手作業 |
| 人が介入した理由 | あいまいな仕様、停止条件、承認など、実際の理由 |
| 所要時間 | 作業にかかった時間 |
| 公開後の差し戻し件数 | 公開後に差し戻しとなった件数 |

集計の保存先・期間、所要時間の起点と終点、数値目標は未決。工場長がこれらの指標を整理し、発注者（人）がハーネス改善と軽・中の自動マージ移行の判断材料にする。数値の収集・集計は今回実装しない。

## 7. ハーネスの構成

AGENTS.md は約 100 行の目次とし、詳細を `docs/` に置く方針。Issue を仕様の正本、`docs/exec-plans/` を計画、`tests/scenarios/` を実行する合格シナリオ、`docs/factory/` を工場の設計の置き場とする。現在のアプリ構成・運用・決定は [ARCHITECTURE](../ARCHITECTURE.md)・[RUNBOOK](../RUNBOOK.md)・[DECISIONS](../DECISIONS.md) を参照し、工場の設計と混同しない。

繰り返し破られるルールは、文章を増やすだけでなく lint・構造テストへ昇格する。CI で読み取り可能な pass/fail を返し、ブランチ保護で必須化する。人の承認が必要な変更は CODEOWNERS と保護設定で守る。昇格対象と具体的な実装は振り返りで判断し、個別の変更として進める。

AGENTS.md の目次化は後続作業。Issue #32 では設計書へのリンク追加にとどめる。
