# ソフトウェアファクトリー設計書 v0.1

人が作るもの・合格条件を決め、AI が計画・実装・検証・レビューを進めるための設計書。最初の製品は M2 トップページ（デザイン案 G）とし、当面は Mac 上の Orca で回す。製品そのものの仕様は各 Issue に書く。

仕様の正本は [Issue #32](https://github.com/selecao-inc/selecao-ai/issues/32)。2026-11-04〜05 の検討を基にした v0.1 で、採用には人（大野）のレビュー・承認が必要。承認の有無は [PR #33](https://github.com/selecao-inc/selecao-ai/pull/33)、採用判断と理由は [ADR-007](../DECISIONS.md#adr-007-ソフトウェアファクトリー方式を採用v01) を参照する。

## 読む順番

全員がこの入口を読み、担当する作業に応じて次の文書へ進む。設計全体をレビューするときはすべて読む。

| 文書 | 書いてあること | 読むタイミング |
|---|---|---|
| [workflow.md](workflow.md) | 工程と成果物、役割と権限、停止・再開、結果と指標 | 発注・計画・担当作業の着手時。工場長は全工程で参照する |
| [verification.md](verification.md) | 合格の証拠、シナリオの変更手順と保護、危険度と承認 | シナリオの作成・変更、実装、検証、レビュー、マージ判断の前 |
| [implementation-status.md](implementation-status.md) | 現在の実装状況、未決事項、後続 Issue 候補 | 工場の導入・改善を計画するとき。工場長は製品投入前にも確認する |

## 0. 原則0：ツール非依存

知識とルールは普通の Markdown とスクリプトで書き、Claude Code・Codex・Gemini のどれでも同じ内容を読んで動けるようにする。特定ツール専用の保存先・hook・コマンドに依存させない。

強制手段は CI・ブランチ保護・CODEOWNERS。ツール内の設定やエージェントの自己申告で代替しない。設計と実装済みの仕組みは区別し、未実装の間は人のレビューで確認する。現在の強制範囲は [実装状況](implementation-status.md#現在の実装状況) に示す。

## 7. ハーネスの構成

ハーネスは、エージェントが作業するための指示・道具・検査の仕組みを指す。AGENTS.md を約 100 行の入口にして詳細を `docs/` に置く方針とし、今回は設計書へのリンク追加にとどめる。

| 置き場 | 内容 |
|---|---|
| AGENTS.md | リポジトリの作業ルールと詳細への入口 |
| GitHub Issue | 作るもの・合格条件の正本 |
| `docs/exec-plans/` | 変更範囲・手順・検証方法の計画（保存・運用の仕組みは未実装） |
| `tests/scenarios/` | 実行する合格シナリオ（未整備） |
| `docs/factory/` | この工場の設計 |

繰り返し破られるルールは lint・構造テストへ昇格し、CI で pass/fail を返してブランチ保護で必須化する。人の承認が必要な変更は CODEOWNERS と保護設定で守る。昇格対象は振り返りで判断し、個別の変更として進める。

現在のアプリ構成は [ARCHITECTURE](../ARCHITECTURE.md)、運用は [RUNBOOK](../RUNBOOK.md)、決定記録は [DECISIONS](../DECISIONS.md) を参照する。Issue #32 の概要 1・2・5・6 は workflow.md、3・4 は verification.md、0・7 はこの入口に対応する。
